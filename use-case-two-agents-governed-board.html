USE CASE · PULSE IN PRODUCTION

Two Agents.
Independent Review.

Requirements, decisions, and test evidence stay linked end to end — so months later, “why does this work this way” still has an actual answer.

02 · PROBLEM

Agentic pipelines are confident. That’s the problem.

Three failure modes this workflow is built to close, not just describe.

Status Can Drift From Reality

A card can be marked done, a sprint can close, tests can be marked passed — while the underlying work was never actually finished. Nothing about a status label guarantees it’s true.

Self-Review Isn’t Review

If the same agent that writes a task is also the one that approves it, “approved” just means the agent still agrees with itself.

A Rule Nobody Enforces Is a Suggestion

A guideline that only warns doesn’t stop bad work from shipping — it just leaves a note next to it on the way out.

03 · ARCHITECTURE

One board. A strict lineage.

Every stage on this board only opens once the one before it is actually in a state that allows it — not merely claimed to be.

  1. Ideation → Refinement → Spec

    An idea is refined and turned into a spec before any task exists. A spec must reach approved before its sprint can open.

  2. Sprint → Tasks

    The sprint’s tasks and their matching tests open once the work they depend on is actually ready, not just scheduled.

  3. Task lifecycle

    Every task moves started → in_progress → validation. The Builder can drive it this far — the preset structurally blocks it from going further.

  4. Validator gate

    Every submission is checked independently. Approved tasks move to done; anything short is sent back with a reason, not silently passed through.

  5. Sprint close-out

    Only once every task is approved and every test has genuinely passed does the Validator submit a sprint evaluation and close it.

Implementation and validation run task by task, not stage by stage: prompt the Builder, then prompt the Validator, and don’t start a task’s dependents until it’s actually approved. If a submission comes back with changes requested, the Builder fixes it and resubmits — the task doesn’t move forward until it’s genuinely cleared.

04 · HOW IT WORKS

Six steps, one shared board.

Every step below is a real captured moment from the pulse-brownfield-feature-demo board — not a mockup.

  1. STEP01

    Ground it in what already exists

    Before drafting the spec, the team reads what the codebase already does and records it as a Pulse Decision — so both agents start from the same ground truth, not assumption.

    Decision recorded before the Sprint opens
  2. STEP02

    Foundation task clears first

    Stage 1 (Foundation): the sprint’s first task has no dependencies. Everything else on the board waits for it to clear review before starting.

    okto_pulse_get_task_context
  3. STEP03

    Independent tasks run in parallel

    Stage 2 (Implementation): once the foundation task is done, two independent tasks open at once and move through the same lifecycle — started → in_progress → validation.

    okto_pulse_move_card (gate: builder != validator)
  4. STEP04

    Independent review checks

    The Validator loads full spec context — including Decisions the Builder may not have referenced — and checks three things: confidence (does the Builder’s account hold up?), completeness (the full requirement, not part of it), and drift (does it match the spec). Short on any one, and it goes back with a specific reason, not a generic rejection.

    okto_pulse_submit_task_validation
  5. STEP05

    Verify test execution evidence

    Stage 3 (Testing): three test tasks, each matched to an implementation task, must actually run their scenario — recording a result as passed isn’t accepted without evidence it executed.

    okto_pulse_submit_task_validation
  6. STEP06

    Close-out sprint & spec

    Stage 4 (Close-out): with all 6 tasks approved, the Validator submits the sprint evaluation and closes it. The spec is marked complete only after that — never before.

    okto_pulse_submit_sprint_evaluation
05 · REFERENCE BUILD

Two real agents. Separate identities.

Two separate MCP connections, each with its own credentials — not one identity switching roles — working the same board end to end.

Builder
Executor
  • Implements each task end to end against the real codebase
  • Submits a completeness estimate and any deviation from spec
  • Moves cards: started → in_progress → validation
  • Cannot submit task validation or self-approve cards
Validator
Reviewer
  • Never implements or modifies code
  • Reviews every submission independently for confidence, completeness, and drift
  • Submits validated test evidence to the board
  • Moves cards: validation → done

Builder runs on the Executor preset and Validator on the Validator preset — two of Pulse’s four board-wide permission presets, enforced structurally, not by instruction either agent could ignore:

PresetCan doCannot do
Spec WriterOwns ideation, refinement, and spec contentCannot move a spec past approved
Executor (Builder)Implements tasks, moves cards through started → in_progress → validationCannot submit a validation or move a card to done
ValidatorSubmits task/spec validation, moves cards validation → doneDoes not implement
QAWrites test scenariosCannot submit any gate
06 · QUICKSTART

Install it. Record the first Decision.

The real install commands, plus the snippet that recorded a baseline convention as a Decision before any new work opened.

  1. 01

    Install the CLI from PyPI

    > pip install okto-pulse
  2. 02

    Initialise local repository data

    > okto-pulse init
  3. 03

    Seed the demo board

    > cp data/pulse.db ~/.okto-pulse/data/pulse.db
    Loads pulse-brownfield-feature-demo with Ideation, Refinement, and an approved Spec already recorded.
  4. 04

    Start Web UI & MCP server

    > okto-pulse serve
    Web UI on port :8100 · MCP server on port :8101/mcp · connect two separate agent identities — Executor and Validator — each with its own credentials.
  5. 05

    Wire up a coding agent

    > okto-pulse init --agents
    Generates a project-local .mcp.json so Claude Code, Claude Desktop, Cursor, or Cline can discover the board and query it directly.
record_decision.py 
# Read what the codebase already does, then record it

add_decision(
    topic="baseline-api-convention",
    summary="Existing routes already define the auth and error-handling "

    recorded_by="card_executor",
)

07 · WHY IT MATTERS

Delivery that actually holds.

Traceable Decisions

Pre-existing conventions are recorded as Decisions before new work starts, aligning both agents on codebase state.

Enforced Role Separation

The agent that builds a task is not the agent that can validate it — enforced by identity on the board.

Enforced Approval Gates

Guideline gates require verified test evidence to be submitted, preventing cards from moving to done without proof.

Full Traceability

Shipped features trace directly back from implementation commits to tasks, test results, and the original spec.
